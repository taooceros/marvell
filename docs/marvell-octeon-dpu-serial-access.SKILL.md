## Host ⇄ card over PCIe (octeon_ep) — WORKING 2026-11-10
- Result: host `ens1` 10.10.0.1/24 ⇄ card `sdp1-0` 10.10.0.2/24; ping 0.17 ms, 1472-byte DF pings OK, ~340 MB/s through ssh; `ssh root@10.10.0.2` with saturn's `~/.ssh/id_rsa` (key added to card `/root/.ssh/authorized_keys`).
- Root cause of "octep_ctrl_mbox : Invalid magic number ffffffffffffffff" (also the user's earlier failure): EBF `P) PCIe Configuration → G) PCIe EP Security` had `A) Allow PCIe Host to Access Octeon Memory (0)`. Host BAR4 reads then fault in the card SMMU: card dmesg `arm-smmu-v3 ... event 0x02` (C_BAD_STREAMID), StreamID 0x3fd20, at the insmod instant. Fix (user-approved, saved): A=1, `S) Host Stream IDs for PEM0` = `0x3ffff` (was 0x30000). Menu: `G` → `A` → `1\r`; `S` → `0x3ffff\r` `\r`; `Q` `Q` `S`. After the save-reboot, stray `[B` chars interrupted U-Boot autoboot → type `boot` at `crb106-pcie>`.
- Card side every boot: `/root/octep_up.sh` (copy in `~/dev/marvell/card-scripts/`). The shipped `/usr/bin/octep_cp_agent` (SDK12.25.10) is the VFIO build (USE_PEM_AND_DPI_PF): needs PEM `0001:00:10.0` and SDP RVU PFs `0002:18:00.0`,`0002:19:00.0` on vfio-pci, run `octep_cp_agent /usr/bin/cn106xx.cfg -- --sdp_rvu_pf 0002:18:00.0,0002:19:00.0 --pem_dev 0001:00:10.0`. Its mailbox is SDP PF0 BAR4 + 28 MiB = phys 0xbfbc00000 = host BAR4 index 7. Auto-loaded `pcie_marvell_cnxk_ep` (legacy-agent helper) repoints PEM0 BAR4_INDEX 7..13 (PEM0 CSR 0x8e0000000000 + 0x700 + 8·i; value = (pa>>22)<<4|1) to its own pages, so the script restores index 7 to firmware's linear map (0xbfa000000 + i·4 MiB → 0x2fef1). Verify: 64-bit read of 0xbfbc00000 = 0xdeaddeadbeefbeef. Then `ip link set sdp1-0 up; ip addr add 10.10.0.2/24 dev sdp1-0` (not persistent).
- Host side: Marvell `pcie_ep_octeon_host` `drivers/octeon_ep` builds cleanly for 6.17.7 (`make CONFIG_OCTEON_EP=m` in that dir; README claims ≤6.6). User loads it: `sudo insmod ~/dev/marvell/pcie_ep_octeon_host/drivers/octeon_ep/octeon_ep.ko` (unsigned → taint, fine; no lockdown). Netdev `ens1`, MAC 00:00:00:01:01:00 (cn106xx.cfg PF mac_addr has only 5 bytes). `sudo ip link set ens1 up; sudo ip addr add 10.10.0.1/24 dev ens1` (not persistent). Agent must be running (fw ready VSEC=1) before insmod; host dmesg needs sudo (dmesg_restrict=1).
- A/B verified 2026-11-10 (EBF already allowing host access, agent running): BAR4_INDEX7 left at the module's page (0x4611) → host `Invalid magic number 0`, no SMMU event; index 7 = 0x2fef1 → works. So "magic ffff…" = SMMU/EBF deny, "magic 0" = index-7 override.
- A failed host setup leaves the VSEC firmware status at 2 (host writes FW_STATUS_RUNNING early in octep_device_setup, octep_cnxk_pf.c:971); the next insmod then loops `Firmware ready status = 2`. Fix: restart the agent (`pkill -INT -x octep_cp_agent; /root/octep_up.sh`), the waiting driver continues and creates `ens1`.
- Why two components: pcie_ep_octeon_target history — 2024-02 vfio path added (agent then wrote BAR4_INDEX7 itself, masking the module); 2025-05-27 `df93f27` moved the mailbox to SDP RVU PF BAR4 and dropped that write. mercury `~/marvell/` holds the user's SDK trail: base/extension sources 12.25.06 (Jun–Jul 2025, its agent already has "directly mapped"), `FW-SDK12.25.08` (2025-09-22), `SDK12.25.10` (2025-11-03), plus official docs `documentation-pcie-ep-generic.zip` (`doc/_sources/ext/ext1/__CNXK-README.txt`, `doc/firmware/ebf/ebf_user_guide.html`). The official README says `modprobe pcie_marvell_cnxk_ep` then run the agent; its vfio note only adds the vfio binds and never says to drop the module → following it hits the index-7 conflict on every SDK the user had. The user's old failure log (`octeon_ep 0001:17:00.0 ... magic ffff…`) came from a host with PCI domain 0001 — not mercury (domain 0000 only); likely venus (no SSH access for the agent).
- Marvell's intended CN10K setup is the vfio agent WITHOUT the module: DAO `doc/guides/gsg/kernel.rst` — "`modprobe.blacklist=pcie_marvell_cnxk_ep` is required only on cn10k platforms" (kernel bootargs); DAO CI `ci/test/dao-test/common/ep_device_utils.sh` binds PEM to vfio-pci, runs `octep_cp_agent cn106xx.cfg -- --sdp_rvu_pf 0002:18:00.0,0002:19:00.0 --pem_dev 0001:00:10.0`, and its cleanup `rmmod pcie_marvell_cnxk_ep`. From WAIT_FOR_FW or failed (ALLOC) state it does not reset. Host BARs survive the chip reset (config space 0x10-0x27 still holds the assigned addresses; non-root can check with `od -t x4 -N 0x28 /sys/bus/pci/devices/0000:99:00.0/config`). Keystrokes typed into the console during that reboot stop U-Boot autoboot → press Enter, then `boot`.
- /dev/mem on PEM CSRs: single 64-bit accesses only (`/root/bar4idx7.py`). Wrapping the 64 KiB ctypes array in `list()` read every offset and raised 14 SEI-UER SErrors (recoverable; agent and link survived) on 2026-11-10.

## Updating CN106 firmware without the 100G cable (researched 2026-11-10, not yet done)
- U-Boot 2023.01-12.25.10 has `ext4load`, `ext4ls`, `fatload`, `md5sum`, `crc32`, `tftpboot`, `nvme` (card has NO NVMe; storage is eMMC, root = mmcblk0p2), `bootimgup`, `bootimgversion`, `bootimgcopy`. Plan: scp `flash-cn10ka-*.img` to the card over SDP, then in U-Boot `ext4load mmc 0:2 $loadaddr /root/<img>` → `md5sum` → `bootimgup -e spi <bus>:<cs> $fileaddr $filesize`.
- `bootimgup` on CN10K ERASES THE SAVED EBF CONFIG BY DEFAULT (`cmd/marvell/bootimgup-cn10k.c`: "Default to erasing EBF config data"; `-e` = do not erase). A plain update wipes Allow/stream IDs/PORTM layout → likely why the user's earlier EBF change vanished. Always pass `-e`, or redo EBF after updating. `-d` = dry run.
- Linux-side official path: ATF "secure firmware update" via `/sys/kernel/debug/cn10k_swup/verification` IOCTLs (CONFIG_MRVL_SWUP=y on the card) taking the `fw-update-cn10ka-*.bin` CPIO; doc copied to `~/dev/marvell/docs/sdk12.25.06-cn10k_firmware_update.txt`. The userspace `mrvl_swup` app is not in the SDK 12.25.06 sources on mercury. `/dev/mtd0`/`mtd1` are writable from Linux (flags 0xc00) but raw writes skip TIM validation; mtd-utils not installed.
- Saved EBF settings live only on SPI0 (FDT at 0x1fd0000); SPI1 has none. Whether a boot from SPI1 reads SPI0's settings is unverified.

## Open the consoles
- If group `dialout` is not active in the session, wrap commands in `/usr/bin/sg dialout -c '...'` (bare `sg` is ast-grep here). After a host reboot it is active.
- `/dev/ttyUSB0`: SoC Linux console (CN106 UART0), 115200 8N1, `venus-marvell login:` / `root@venus-marvell:~#` (root password: ask user).
- `/dev/ttyUSB1`: Zephyr MCU (NXP RT1176, FW 1.6.2) shell `uart:~$`. Safe: `help`, `<cmd> -h`, `version`, `kernel uptime`, `net iface`, `net stats <n>`, `device list`, `net ping -c N -I <iface> <addr>`. NEVER `env list` (shell stack overflow → halt). Avoid `ap reset/power`, `flash` unless asked.
- Only one process may hold a tty. `pgrep -a screen` / `screen -ls`; free with `screen -S <pid> -X quit`.

## MCU shell input hazard (caused the 2nd MCU crash)
- The MCU UART DROPS CHARACTERS on fast input (no flow control): `devmem 0x40420004 32` arrived as `devmem 0x40004 32` → BUS FAULT → halt. Always use `zj_mcu.py PANE 'cmd'` (4 chars/150 ms, compares echo, Ctrl-U + abort on mismatch). To repeat a command, Up-arrow + verify + Enter (`zj_mcu_repeat.py`).
- Never `devmem` an unverified address. Verified: ENET(10/100) regs 0x40424000 (EIR +0x04, EIMR +0x08, ECR +0x24, MMFR +0x40, MSCR +0x44 = 0x14e); ENET_1G 0x40420000 (same layout).
- Long MCU output: read the screen log (`/tmp/dpu_ttyUSB1.log`, flushes ~10 s); `dump-screen` shows only the viewport.

## MCU recovery
- Does NOT reset a halted MCU: CN106 Linux/EBF reboot; pulsing the 5 host CP2105 GPIOs (`gpiochip1`/`gpiochip2`; write-only, `gpioget` error 524); host warm reboot (card stays powered).
- DOES: real host power cycle (`sudo ipmitool chassis power cycle` via /dev/ipmi0, no BMC password). MCU is fed from host main power (uptime matches host power-on). Fallback: unplug AC.
- After a power cycle the host I350 (`enp23s0f1`) has NO carrier with the MCU's RJ45 port until CN106 Linux is rebooted once (carrier came up ~4 s into the CN106 reboot and stayed). Host IP 192.168.3.1/24 is not persistent (user adds it with sudo).
- Host↔MCU works then: `ping -6 fe80::4260:5aff:fe02:ed6e%enp23s0f1` (MCU iface 1, MAC 40:60:5A:02:ED:6E). No DHCP server on the p2p link → MCU has no IPv4; Redfish over link-local IPv6: no response.

## RJ45 / internal topology (R4 board)
- Observed: the MCU's ENET_1G MDIO bus finds only PHY1 = 88E1512 (0x0141/0x0dd1), the RJ45 side. The 88E1111 (ID 0x0141/0x0CC2 at addr 0, read through the pad remux below) sits between MCU ENET 10/100 (MCU iface 2, fe80::4:9fff:fe48:838a) and CN106 eth4 (RPM2 LMAC0, SGMII).
- MCU FW 1.6.2 does NOT forward between its ports (tested 2026-11-10 with host⇄MCU and CN106⇄MCU both pinging): no L2 bridge (`net help` has no `bridge`; ARP/ND from host to the card FAIL) and no IPv6 routing (MCU `net ipv6 add 1 fd00:1::2`, `net ipv6 add 2 fd00:2::2`; card fd00:2::41/64 + route fd00:1::/64 via fd00:2::2; host fd00:1::1/64 + route fd00:2::/64 via fd00:1::2 → host reaches fd00:1::2 and fd00:2::2, but fd00:2::41 echoes are counted as iface-1 "IPv6 drop", forwarded 0, even with a reachable MCU neighbor entry for fd00:2::41). `net ipv6 add` and `net nbr` are safe. Host→card therefore needs the PCIe octeon_ep path or an MCU FW that bridges.
- MCU FW 1.6.2 static analysis (image-0 dumped read-only via `flash read is25wp128@0 0x<off> 2000` = hex byte count, 54 chunks, ~5.5 min; rebuilt with SHA256 TLV verified; copy at `~/.local/share/dpu-tools/mcu_fw_1.6.2_image0.bin`): Zephyr 3.6.99; app modules mrvl_ap, mrvl_redfish, mrvl_rest_api, mrvl_http_server, mrvl_sock (RMCP/ASF ping only), mrvl_eeprom_emu, mrvl_mmc, mrvl_dns, task_service; PHY drivers phy_marvell_88e1111 / phy_marvell_88e1510. NO net_eth_bridge, no `net bridge`, no CONFIG_NET_ROUTING forwarding (only net_route), no app-level relay, both ENETs non-promiscuous (RCR PROM=0). So 1.6.2 cannot bridge host↔CN106 at all. MCU flash map: is25wp128 (mcuboot 0x0, image-0 0x20000, image-1 0x321000, scratch, eeprom-target, storage 0x651000 = littlefs `/lfs`, env vars as files in `/lfs/env/`, only `bmc_mac`); w25q256 = CN106 SPI1 (`firmware` 0x0, `config` 0x1e20000). ## Internal link root cause (CN106 side) and status
- WORKING RECIPE (2026-11-10, CN106⇄MCU ping both ways, 1000-byte pings 20/20, ~3 ms RTT, link at 10M): (1) MCU pad remux (below), 88E1111 page 1 (`reg22=1`): write reg0 = 0x13C0 (SerDes AN enable + restart; reads back 0x11C0), `reg22=0`, restore pads. 88E1111 then sends MAC-side 0x4001; reg4 is not writable (stays 0x0001). (2) CN106 LPCS: DEV_ABILITY r4 = 0x9001 (link up, FD, 10M, bit0), IF_MODE 0x0003 (speed from SGMII AN), CONTROL 0x1340 → STATUS 0x002d, PARTNER 0x4001, ATF `eth4 NIC Link is UP`, real carrier, no fake_link needed. MCU logs `eth_nxp_enet_mac: Link is up` only when the CN106 word has link bit 15 set (88E1111 reg17 real-time link follows it; without it Zephyr marks iface 2 down → "Failed to send ping -5"). 100M did NOT work: DEV 0xD401 + IF_MODE 0x0005 → CN106 RX fine but its TX follows the AN-resolved speed (10M from partner 0x4001) → CRC errors at the MCU. Volatile: 88E1111 config lost on host power cycle; LPCS values may be rewritten by ATF link events. MDIO write via ENET_1G: MMFR = 0x50020000 | phy<<23 | reg<<18 | data, then W1C EIR 0x800000.
- The MCU 10/100 MDIO is NOT hung: Zephyr polls the 88E1111 (phy@0) and each poll ends with "write reg22=0", so MMFR always shows 0x505a0000 and EIR.MII is cleared immediately. Remuxing GPIO_AD_33 away makes Zephyr log `Link is down` for iface 2.
- CN106 RPM2 SGMII PCS (MTI LPCS) does SGMII in-band AN as MAC side and waits for the 88E1111, which sends nothing. Read via /dev/mem on the card (64K pages: mmap offset 64K-aligned; STRICT_DEVMEM off): RPM2 BAR0 0x87e0e2000000 (`/sys/bus/pci/devices/0000:01:10.2/resource`), LPCS lmac0 at +0x30000, 16-bit regs on 8-byte stride: CONTROL r0 (0x1140 = AN on), STATUS r1 (bit2 link, bit5 AN done), DEV_ABILITY r4, PARTNER_ABILITY r5 (0x0000), IF_MODE r0x14 (0x0003). `ethtool -s eth4 ... autoneg off advertise 0x8` does NOT change these.
- Runtime force: IF_MODE=0x0005 (SGMII, no SGMII AN, 100M) + clear CONTROL bit12 → STATUS 0x000d. MCU→CN106 then WORKS (MCU `net ping -I 2` NS frames arrive clean in rpm/NIX RX stats). Card scripts: `/root/lpcs.py` (dump), `/root/lpcs_force.py 100|1000|10`, `/root/rx_test.py SPEED SECS` (force + RX stat deltas; run in background while the MCU pings). ATF rewrites the PCS (CONTROL 0x1140, IF_MODE 0x0003/0x0007, DEV_AB 0x0001) on its link events → re-run force afterwards.
- Linux carrier without a kernel module: `/root/fake_link.py up` writes an ATF-style async LINK_CHANGE word (`1 | 1<<3 | up<<9 | 1<<10 | speed<<11`, speed 1=10M 2=100M 3=1G) to RPM2 lmac0 event reg 0x1050 and kicks SW_INT_W1S 0x188 → `eth4 NIC Link is UP 100 Mbps Full`, LOWER_UP. Only fools Linux.
- REAL BLOCKER (CN106→MCU): ATF gates TX unless the PCS reports AN complete. Proof with serdes diag NEA loopback (`modprobe cn10k_serdes_diag`; `echo "5 1" > /sys/kernel/debug/serdes_diagnostics/loopback`, `"5 0"` off; `/root/lb_test2.py LBTYPE CONTROL IF_MODE [DEV_AB]`): AN on + IF_MODE 0x0003/DEV_AB 0x4001 → AN completes, ATF logs `Link is UP 1000`, own frames loop back; any AN-off setting → MAC still counts "transmitted OK" but nothing leaves; switching AN off after completion keeps TX flowing ~0.4 s until ATF polls and logs DOWN. CMR_CFG/COMMAND_CONFIG/XIF_MODE are identical in both states (gate location unknown). MCU ENET MIB (enable: `devmem 0x40424064 32 0x0`; RMON_R_PACKETS +0x284, RMON_T_PACKETS +0x204; offsets = Linux fec.h) confirms the MCU receives 0 frames. 88E1111 never answers SGMII AN (PARTNER 0 in MAC role and in PHY role DEV_AB 0x9401) → needs 88E1111 config via MDIO or an ATF honoring AN-off.
- TX FIR / polarity are not the cause: tried TX polarity 1 (`echo "5 0 polarity 1" > tx_params`), main 35 and 63.
- 88E1111 is NOT the blocker (both directions pass data): `/root/window_test.py DEV_AB SETTLE` opens the ATF gate by self-negotiating in NEA loopback (IF_MODE 0x0003, CONTROL 0x1340), then loopback off + force 0x0005 and blasts raw frames for 3 s before ATF re-gates (~2.5 s). DEV_AB 0x1401 (partner 0x5401 → 100M FD) → MCU MIB IEEE_R_FRAME_OK +2 clean frames; DEV_AB 0x4001 (resolves 10M) → 19 CRC-error frames; DEV_AB with link bit 15 (0x9401) never completes AN in loopback. The ATF gating in EBF 12.25.10 is what blocks TX.
- /dev/mem on RPM: ONLY 64-bit ctypes accesses to known registers. Python `m[o:o+8]` byte reads raised an "SEI-UER recoverable" SError; so did one 64-bit sweep over 0x8/0x80/0x1070/0x4100/0x4118/0x4120/0x5B08/0x8100 + LPCS r6/r0x12/r0x13 (culprit not isolated; 0x4118 and 0x5B08 read back all-ones). Known-safe: 0x0 CMR_CFG, 0x8010 COMMAND_CONFIG, LPCS r0/r1/r4/r5/r0x14, 0x1050 event, 0x180/0x188 SW_INT.
- 88E1111 MDIO ACCESS WORKS via pad remux (user-approved, read-only, 87 s, restored + verified): ENET_1G MDC/MDIO onto the 88E1111 pads — `devmem 0x400e818c 32 0x9` (GPIO_AD_32 alt9 ENET_1G_MDC, orig 0x3), `devmem 0x400e8190 32 0x9` (GPIO_AD_33 alt9, orig 0x3), `devmem 0x400e84c8 32 0x3` (ENET_1G MDIO input daisy → AD_33, orig 0x1); then `mcu_mdio.py PANE 0 REG...`; restore in reverse order. While switched the 88E1512 (phy1) replies are not heard. Readings (page selected by reg22 unknown, not read): reg2/3 = 0x0141/0x0CC2 (88E1111 confirmed, addr 0); reg27 = 0x848E (HWCFG_MODE 0xE, fiber/copper auto-select disabled, serial AN bypass off); reg0 = 0x01C0 (AN enable bit12 = 0, full duplex); reg1 = 0x0149 (no 10/100 ability bits → looks like the fiber/SerDes page; link bit latched low, read once); reg17 = 0x4C10 (resolved, real-time link up, 100 Mbps, duplex bit 0 = half). So the 88E1111 SerDes AN is simply disabled. The ENET(10/100) MDIO engine itself is hung (MMFR stuck 0x505a0000 = write PHY0 reg22=0, writes ignored, EIR.MII never sets), so the MCU FW likely never finished configuring it. MCU ENET_1G MDIO on its own pads (write MMFR 0x60020000|phy<<23|reg<<18, read MMFR, W1C EIR 0x800000): scan 0-31 finds only PHY1 = 88E1512 (0x0141/0x0dd1). CN106 SMI1 (gpio54/55) reads of addr 0 all return 0x0000 (also with slower MDC via `/root/smi_slow.py BUS PHY PHASE REG...`); MDIO pin idles high. `/root/smi.py BUS PHY REG...` (temporarily sets c22, restores CLK).
- MCU MII pinmux looks consistent: console LPUART1 owns GPIO_AD_24/25, so ENET RX_EN/RX_ER sit on DISP_B2_08/09 (alt1, daisy 1); other MII pins on GPIO_AD_12..31.
- In U-Boot (key at "Hit any key"): no `mdio`; `ethlist`, `get_mode`, `phy_read` (fails for RPM2: no PHY bound), `sdes_rx <portm> [lane]` (PORTM5 = GSERM2 lane0: "Signal detected"), `sdes_tx`.

## CN106 GPIO on the DPU
- libgpiod v2 in `/usr/local/bin`: `gpioinfo -c gpiochip0`, read as-is `gpioget -a -c gpiochip0 N`. Observed: gpio_5, gpio_43 and gpio_50 read 1 (gpio_50 is an input); don't toggle CN106 GPIOs blind. GPIO_BIT_CFG(n) at 0x803000000400 + 8n (pin_sel bits 26:16).

## Inspect / change card networking
- `ip -br link`, `ethtool ethN`, `cat /sys/class/net/ethN/carrier`; `cat /sys/kernel/debug/cn10k/rvu_pf_rpm_map`; per-lane `/sys/kernel/debug/cn10k/rpm/rpmX/lmacY/{fwdata,stats}`.
- EBF: reboot, `B` within 10 s → `S` → `E` → PORTM → `1` → protocol → FEC `0\r` → `Z` `Z` → `S` save (auto-reboots); `X` exits discarding.
- rvu-nicpf `ethtool -s` must include `advertise <hexmask>` (0x8 100baseT/Full, 0x20 1000baseT/Full, 0x1000 10000baseT/Full); omitting it breaks the port.

## Risks
- Get user approval before EBF saves or risky MCU pokes. Card reboots never disturbed host PCIe 99:00.0 (driver unloaded each time).
- Card root uses password auth; never put it on a shared network before hardening SSH.
