# Marvell OCTEON 10 DPU workspace

Host `saturn` (x86_64, Ubuntu 22.04, kernel 6.17) with an OCTEON 10 CN106xx `crb106-pcie` card at PCIe `0000:99:00.0` (Gen5 x4). The card runs Ubuntu 24.04 on SDK13.26.10 firmware and kernel 6.12.51 (linux-marvell `linux-6.12.x-release-v26.10`).

Work is tracked in Linear team **Marvell** (`MRV`, workspace `taooceros`): one Done issue per finished piece, open items as children of MRV-13 ("主机 ⇄ CN106 数据通路"). Add new results to the matching issue instead of creating duplicates.

## Linear

- Identity: agents on saturn write to Linear as the agent app **saturn-omp**. `~/.omp/agent/mcp.json` takes its header from `~/.local/bin/linear-agent-token --header` (client-credentials token from `~/.config/linear/credentials`, renewed when under 5 days are left; `--restore` switches back to the personal API key), but a session started before that switch still talks to the MCP server as the user, and so do its subagents. Read through MCP; write with `linear-app` (`comment`, `state`, `describe`, `create`, `gql`; see `linear-app --help`), which always acts as saturn-omp. A comment posted as the user reads as a request from the user.
- Polling session: when the user says `poll`, the session becomes the dispatcher. `mrv-poll` (`~/.local/bin`) runs Mailstream's `linear-poll.py` (`~/.local/share/linear-poll/`; line formats in its docstring) against MRV as saturn-omp, with claims in `~/.local/state/linear-poll/`. Start `mrv-poll watch` as a background job with no deadline; it exits with the lines of the first pass that has any. Hand each line out, mark it with `mrv-poll seen issue|comment <id>` (👀), and start the watch again.
  - `issue`: an issue in Todo, created by the user or saturn-omp and not yet commented on by an app, or one labelled `omp`. The user files work in Todo. Agents file their own issues in Backlog (`linear-app create MRV <title> --parent MRV-13`) and move an issue to Todo only together with a comment asking the user something.
  - `comment`: a user comment on any MRV issue from the last 7 days. It goes to the agent that works the issue (`write agent://<id>`), or to a new one. A "可以" / "ok" answering an agent's question is the approval the hardware rules below ask for.
- One card at a time: there is one card, so at most one agent at a time touches the card, the host DPDK/VF setup or `testbed/` in this checkout. The dispatcher queues the rest and says so on the issue. Agents that only read (code, logs, Linear) or only write Linear run alongside. The directory is a colocated jj repo (`jj st`, `jj log`; describe changes with the issue id, `jj new` after each piece, never rewrite another agent's changes). Agents that only change code may work in their own checkout (`jj workspace add ../marvell-<issue>`), which lacks the ignored trees (`marvell-dpdk/`, `sysroot-card/`, …), so builds and runs against the card still happen here. In such a checkout give every tool absolute paths inside it: relative paths resolve against the session's directory, this checkout (MRV-17 edited `testbed/` here that way). Card cross builds there point at this checkout's `sysroot-card/` through the environment; a symlinked sysroot fails to link (`libmvec.so.1`).
- Agents working an issue: on start, `linear-app state <issue> "In Progress"` and a comment `[omp @ saturn:~/dev/marvell · <model>] start (<agent id>): <plan>`. Results land on the issue as comments (numbers with the command that produced them). A question for the user: a comment, then `Todo`. Finished: a summary comment, then `In Review`; the user moves it to Done.

## Testbed

- Write the testbed in Rust: host-side and card-side benchmark programs, experiment drivers, and result collection.
- Do not add new C or shell benchmark programs. The C and shell tools in `bench/` (`udp_pingpong`, `udp_blast`, `dpdk_pingpong`, `dpdk_reflector`, testpmd drivers) are prototypes from the first measurements: port their behavior to Rust instead of extending them, and keep them only until the Rust version reproduces their numbers.
- `testbed/` is a Cargo workspace: `dpdk-sys` (bindgen bindings; DPDK's static inline fast path is exported through bindgen's `wrap_static_fns`, linked statically from `pkg-config --static libdpdk` of the build target; the archives are tracked, so a rebuilt DPDK relinks), `dpdk` (small safe layer: `Eal`, `Mempool`, `Port`, `Mbuf`, `Burst`, `Memzone`, `HostDma` (DPI to or from host memory, `HostDir`), all borrowing the `Eal`), `testbed` (library: wire format, `closed_loop::ClosedLoop` driver with `Replies` sources, `inline` cell format, control area and rings, `mmio`; binaries: `pingpong`/`reflector` over SDP, `inline_pingpong` (host, x86_64)/`inline_reflector` (card, aarch64, root) over the PF BAR4 window, replies over SDP, written into a host ring by card DPI DMA (`--dma`) or card core stores (`--store`), or pulled by the host with one 16 B BAR4 read (W=1); `inline_stream` (host) drives open-loop streams against the same reflector: `--dir h2c --via movdir|fetch|both|hybrid` (card only checks), `c2h` (card writes unprompted), `bidir` (h2c and c2h at once, independent), `split` (one host core sends, another takes replies; `--window W` caps requests outstanding, 1 = ping-pong; `--via fetch|hybrid` too); `inline_pingpong --probe-reads` and `inline_reflector --timing` time the pieces). Card cores take roles (`inline_reflector --roles ring|source|fetch,...`): `ring` serves the BAR4 request ring, `source` writes card -> host streams, `fetch` reads a request ring in host memory with DPI reads (`--fetch-dma VF`, `--fetch-chunk` cells per read × `--fetch-depth` reads in flight) instead of having requests pushed through BAR4. The fetch core reads speculatively (whole chunks ahead, whether written or not) unless the host sets `FETCH_TRIGGER` and the card has no ring cores: then it reads only what MOVDIR64B doorbells in the BAR4 ring publish (`Cell::doorbell`: `tag` = an inline message or 0, `tsc` = fetch-ring cells published), which is `--via hybrid` (`--batch` messages per round, `--inline` of them carried by doorbells; `split` needs `--inline 0`, as inline messages get no reply). New DPDK calls go into `FUNCTIONS` in `dpdk-sys/build.rs` (and `wrapper.h` for macros and bitfield structs), never as hand-written `extern` blocks.
- Build inside devenv, which sets all per-target toolchain variables: `devenv shell -- sh -c 'cd testbed && cargo build --release'` for the host (links `marvell-dpdk/build-host`, octeon_ep VF PMD) and the same with `--target aarch64-unknown-linux-gnu` for the card (links the card's `dpdk-24.11-cn10k` from `sysroot-card/` through Ubuntu's `aarch64-linux-gnu-gcc`). Copy card binaries with `scp`; refresh the sysroot with `devenv shell -- card-sysroot-sync` after card package changes.
- Keep `batch` and `concurrency` separate (terminology from `~/dev/accel-datapath`): batch = packets per doorbell (one `rte_eth_tx_burst` call), concurrency = maximum messages outstanding. Every reported number states both, and message rate (Mmsg/s) is reported together with bandwidth.
- Every run must verify its data, not just count it: each reply is matched to its outstanding request (seq + tsc), frames and cells carry a trailing seq copy, and the bins fail on bad or torn replies. Timestamp arrivals with `dpdk::rdtsc_after_loads` (RDTSCP; LFENCE;RDTSC measured the same): plain RDTSC after an MMIO poll executed early and under-measured the inline RTT by ~0.5 µs. Cross-check W=1 RTT against 1 / message rate.
- Host uncore frequency moves W=1 latency by up to ~0.3 µs: it idles at 0.8 GHz and ramps over seconds, so results came in two "modes" (0.92 vs 1.23 µs for the same path). For comparable numbers, pin it first (`sudo bench/host_power.sh pin`: uncore 2.2 GHz on both packages, performance governor on cpu40/104; `restore` undoes it; both leave `current_freq_khz` readable for monitoring). Device-side memory reads in hot loops: read cells word by word (`Cell::poll`), never `read_volatile` of a struct holding a byte array (compiles to 64 byte loads plus a store-forwarding stall).

## Hardware access

- Root-only host steps live in scripts the user runs with sudo (`bench/host_dpdk_up.sh`, `bench/host_dpdk_down.sh`, `bench/host_power.sh`, `bench/host_boot_persist.sh`).
- Card control path: `ssh root@10.10.0.2` over host PF `ens1` ⇄ card `sdp1-0`. DPDK data path: host VF0 `0000:99:02.0` ⇄ card `sdp1-1` (`0002:01:00.2`). Never give `sdp1-0` to DPDK; that cuts ssh.
- Boot: the card starts its side by itself (`octep-cp-agent.service` runs `/root/octep_up.sh --foreground`; `sdp1-0` 10.10.0.2/24 from `/etc/netplan/60-sdp1-0.yaml`; backups of the files this replaced in `/root/mrv19-backup/`). `sudo bench/host_boot_persist.sh install` makes the host side survive host reboots (octeon_ep at boot, `ens1` 10.10.0.1/24 through systemd-networkd, `perf_event_paranoid`). A card reboot the host did not start leaves `ens1` down for good (octeon_ep only drops the carrier when the heartbeat stops; seen 2026-11-16 after `systemctl reboot` on the card): `sudo bench/host_boot_persist.sh reload` reloads octeon_ep, which resets the card once more, waits for it and recreates the host VFs. So reboot the card with `reload` rather than from the card. Not loaded at boot: `pem_wc`, the card's hugepages and `sdp1-1` for DPDK (`/root/bench/dpdk_up.sh`), the host's `bench/host_dpdk_up.sh` and `host_power.sh`.
- Get the user's approval before EBF saves, firmware flashes, and card reboots.
- Card CSRs through `/dev/mem`: only single 64-bit loads of known registers, as `card-scripts/bar4idx7.py` does (`q = (ctypes.c_uint64 * 8192).from_buffer(m)`, then `q[off >> 3]`). Never slice the mmap (`m[o:o+8]`) or iterate the array: a sliced read of BAR4_INDEX15/REG_NORM_ACC on 2026-11-13 raised 5 SEI-UER at once (count 3 → 8), and `list()` over the array raised 14 on 2026-11-10. EDAC logs them seconds late, so recheck the count after ~20 s.
- Host PF BAR4 = 16 × 4 MiB windows into card memory (`BAR4_INDEX` in PEM0 CSRs); slot 7 is the octep control mailbox. Only `inline_reflector` repoints a slot (15) and restores it on exit; the host writes BAR4 only after reading the reflector's READY cookie in that slot.
- Card DPI DMA: PF `0000:06:00.0` (`octeontx2-dpi`), four VFs `0000:06:00.1`-`.4` on vfio-pci: one per `inline_reflector` core for `--dma`, plus one for `--fetch-dma` (approved 2026-11-10 and 2026-11-13; created at boot by `dpi-vfs.service`, `/root/dpi_vfs_up.sh`). DMA writes and reads go out as host VF0 (DPI func pf 0, vf 1) and must target IOVAs in the host DPDK process's memzones; the host IOMMU is on.
- Card core → host stores: PEM0 outbound region table `PEM0_REG_NORM_ACC(i)` at `0x8e00_0000_4000 + 16·i` (256 regions × 2 GiB of core address space at `0x8800_0000_0000 + i·2 GiB`; geometry in `PEM0_CONST_ACC` at `+0x218`), found by disassembling the EBF in `fw-backup/` and decoded with the CN9 BDK headers in coreboot. All zero in EP mode. `inline_reflector --store` claims region `255 - core` per core (approved 2026-11-12), points it at the host reply ring as host VF0 (`vf_active`, vf 0) and restores it on exit. Store only: a load through a region the host does not complete raises an SError. Never read guessed CSR offsets (CN10K offsets differ from the CN9 BDK); reading `0x87e0_0300_1000` (a register only the secure-world EBF reads) caused SEI-UER #3. `--store-wc` maps the regions write-combining through `pem_wc` (loaded first) and stores each reply as 4 contiguous `STP`s: the core gathers them into one 64 B write, ~3× the Device-mapped rate; the host must check every part of a reply, since gathering occasionally fails and the pieces land in any order.
- Write sizes arriving at the host are measurable: `perf stat -a -e 'uncore_iio/event=0x84,ch_mask=0xff,fc_mask=7,umask=1/,uncore_iio/event=0x83,ch_mask=0xff,fc_mask=7,umask=1/,unc_cha_tor_inserts.io_itom'` (line writes, 4-byte data units, full-line ItoM; `nix shell nixpkgs#perf`; needs `kernel.perf_event_paranoid` ≤ 0, set to 0 on saturn since 2026-11-13, kept across host reboots by `bench/host_boot_persist.sh install`). With `umask=4` the same two events count the card's reads of host memory; `event=0xc1`/`0xc0` with `umask=1` count CPU writes to the device (MOVDIR64B).
- Multi-core card side: `inline_reflector -l 3-6 ...` polls with one core per EAL lcore (core i takes ring seqs with `(seq-1) % n == i`), one SDP TX queue per core; the SDP delivers card TX queue i to host VF RX queue i, so the host opens as many RX queues as the card publishes cores (`CORES_OFFSET`) and polls them all.
