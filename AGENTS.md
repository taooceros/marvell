# Marvell OCTEON 10 DPU workspace

Host `saturn` (x86_64, Ubuntu 22.04, kernel 6.17) with an OCTEON 10 CN106xx `crb106-pcie` card at PCIe `0000:99:00.0` (Gen5 x4). The card runs Ubuntu 24.04 on SDK13.26.10 firmware and kernel 6.12.51 (linux-marvell `linux-6.12.x-release-v26.10`).

Work is tracked in Linear team **Marvell** (`MRV`, workspace `taooceros`): one Done issue per finished piece, open items as children of MRV-13 ("主机 ⇄ CN106 数据通路"). Add new results to the matching issue instead of creating duplicates.

Focus (MRV-49, 2026-11-17): the direct paths through BAR4 and MMIO (host MOVDIR64B into card memory; card core stores, write-combining stores and DPI writes into host memory) are the subject now. SDP is good enough as it stands: no new SDP-only experiments or tuning; SDP stays as a reference line in comparisons and as the control path. When an experiment or review proposes SDP work, say so on the issue and leave it in Backlog.

Knowledge shared with `~/dev/accel-datapath` (MOVDIR64B ordering and write path, uncore counters, uncore/core clocks, RDTSC/RDTSCP, batch/concurrency terms, closed-loop method, saturn's shared-host rules) lives in `~/dev/datapath-kb`; read its `AGENTS.md` and `README.md`. Put a new cross-project fact there with a source link; keep card-specific detail here.

## Linear

- Identity: agents on saturn write to Linear as the agent app **saturn-omp**. `~/.omp/agent/mcp.json` takes its header from `~/.local/bin/linear-agent-token --header` (client-credentials token from `~/.config/linear/credentials`, renewed when under 5 days are left; `--restore` switches back to the personal API key), but a session started before that switch still talks to the MCP server as the user, and so do its subagents. Read through MCP; write with `linear-app` (`comment`, `state`, `describe`, `create`, `figure`, `gql`; see `linear-app --help`), which always acts as saturn-omp. A comment posted as the user reads as a request from the user.
- Polling session: when the user says `poll`, the session becomes the dispatcher. `mrv-poll` (`~/.local/bin`) runs Mailstream's `linear-poll.py` (`~/.local/share/linear-poll/`; line formats in its docstring) against MRV as saturn-omp, with claims in `~/.local/state/linear-poll/`. Start `mrv-poll watch` as a background job with no deadline; it exits with the lines of the first pass that has any. Hand each line out, mark it with `mrv-poll seen issue|comment <id>` (👀), and start the watch again. The dispatcher keeps its own context small: before handling each poll result (or an agent's report) it opens a `checkpoint`, does the reading and dispatching inside it, and `rewind`s once the tasks are out, keeping only a short report (what went to whom, the card queue, decisions owed by the user). It does not relay to the user what agents did; their results are on Linear.
  - `issue`: an issue in Todo, created by the user or saturn-omp and not yet commented on by an app, or one labelled `omp`. The user files work in Todo. Agents file their own issues in Backlog (`linear-app create MRV <title> --parent MRV-13`) and move an issue to Todo only together with a comment asking the user something.
  - `comment`: a user comment on any MRV issue from the last 7 days. It goes to the agent that works the issue (`write agent://<id>`), or to a new one. A "可以" / "ok" answering an agent's question is the approval the hardware rules below ask for.
  - Thin forwarding (MRV-131): pass user comments straight through verbatim (`MRV-<N>`, comment text, and lock/state only if changed) without rewriting, checklists, or instructions. Keep new-issue dispatches minimal too (issue id, workspace path, lock/read-only status); let the agent read the issue and `AGENTS.md` and figure it out itself.
  - Subagent context cap (MRV-132): any subagent uses at most **500k** context; proactively hand off (post a concise handoff comment on the issue and exit cleanly) before exceeding 500k, and the dispatcher spawns a fresh subagent instead of reviving one near/over 500k.
- One card at a time: there is one card, so at most one agent at a time touches the card, the host DPDK/VF setup or `testbed/` in this checkout. The dispatcher queues the rest and says so on the issue. Agents that only read (code, logs, Linear) or only write Linear run alongside. The directory is a colocated jj repo (`jj st`, `jj log`; describe changes with the issue id, `jj new` after each piece, never rewrite another agent's changes). Agents that only change code may work in their own checkout (`jj workspace add ../marvell-<issue>`): `devenv.nix` automatically falls back to `../marvell/{marvell-dpdk,sysroot-card}` so host and aarch64 cross builds work directly inside secondary workspaces without symlinks (a symlinked sysroot fails to link `libmvec.so.1`), while live runs against the card still happen under `nic-lock`. In a secondary checkout give every tool absolute paths inside it: relative paths resolve against the session's directory (MRV-17 edited `testbed/` here that way).
- Experiment code lands in `main` (MRV-262): the historical `experiment, not for main` side-branch habit is abolished. Reusable infrastructure (`dpdk-sys`, `dpdk`, `testbed::{mmio, lease, inline, bar4_nc, dsa, hist, pmu, rt}`, `card-kmod/{pem_wc,bar4_mair}`, `testbed/mc-adapter/`, `bench/`) lives in `main`. After landing on `main`, forget and remove the temporary `../marvell-<issue>` workspace (`jj workspace forget <name>` and `rm -rf ../marvell-<issue>`) so stale checkouts do not accumulate.
- Agents working an issue: on start, a comment `[omp @ saturn:~/dev/marvell · <model>] start (<agent id>): <plan>` and `In Progress`. `In Progress` means "an agent is working on it now" (MRV-64): the issue whose agent holds the card is always In Progress, and work that doesn't touch the card is In Progress while its agent runs too. The issue holding the card carries the label `nic-lock` (exactly one issue at a time): the agent adds it when it takes the card (`linear-app label <issue> +nic-lock`) and removes it when it has restored the card (`-nic-lock`); the dispatcher checks it on every card hand-over. The agent moves its issue out of In Progress (In Review, or Todo with a question) when it stops. Results land on the issue as comments (numbers with the command that produced them). A question for the user: a comment, then `Todo`. Finished: a summary comment, then rewrite the issue description so it reads as the current state (MRV-42): the conclusion first (it answers the title; for an experiment, whether the hypothesis held), its main figure, what is still open, links to the key result comments, the original 想学到什么/假设/怎么判 kept below; back up the old text to `~/.local/state/linear-poll/desc-backup/<issue>-<date>.md` first and write with `linear-app describe`. Every open item that is real work (a next experiment, an untested part, a known bug) becomes its own sub-issue of the finished issue in Backlog (`linear-app create MRV <question-style title> --parent <issue> --state Backlog`, MRV-33 framing; merge items one run would answer; skip ones already filed), and the description's open list links them (MRV-44, MRV-48). Then `In Review`; the user moves it to Done.
- Experiment issues (MRV-33): the title is the question the experiment answers, i.e. what we learn ("13 M/s 时到底是哪一级在排队？"), not the procedure. The description starts with three short paragraphs written before any run: **想学到什么** (what we learn and why it matters), **假设** (the hypothesis), **怎么判** (which result confirms it and which refutes it). The method and conditions follow. Every experiment report — results comment, summary, review answer, finished description — opens with the hypothesis and its verdict, before any number (MRV-67): `**假设**：<one sentence> → **结果**：成立 / 不成立 / 部分成立 / 没测到（<one sentence why>）`. A run that tested something other than the stated hypothesis says so in that line, and a new hypothesis gets its own issue (MRV-66).
- One question per issue (MRV-66): an issue answers its title and nothing else. A side finding, a new suspect or a reviewer's alternative explanation becomes its own Backlog sub-issue (one question, MRV-33 framing) instead of growing the issue; the issue only links it. Descriptions stay short: the answer to the title (one paragraph), one figure, open items as links to their sub-issues; method details, tables of every run and history go into the collapsed agent notes. Results and review-answer comments follow the same limit: answer the question asked, link the rest.
- Occam's Razor in experiments and reports (MRV-82): prove each point with the **simplest setup** and **one variable changed at a time** (e.g. fix the fastest direct path `MOVDIR64B + 写合并 (WC)` and vary only the single knob under test, instead of running a full `WC × ST × DPI × 1c × 4c × W` matrix by default). In every experiment issue and conclusion sub-issue, explain in plain Chinese what the fixed baseline setup is and what every parameter/knob does before showing the single-variable comparison; when synthesizing multiple conclusions, give each distilled conclusion its own child sub-issue with its single-variable figure. This is the default for designing **and** presenting every experiment from now on (user on MRV-82, 2026-11-18: "以后做和讲实验都要这么做"): the title states the finding in one sentence, the report opens with the single-variable chart plus a mechanism diagram that shows *why* (as in MRV-85/MRV-86), and terms are defined in one line where first used.
- Issue references (MRV-43): never a bare "MRV-17". In Linear text, link it and say what it is: `[MRV-17 主机侧多核](url)`; `linear-app comment/describe/create` rewrites bare identifiers into such links automatically (titles over 24 characters are cut), so write the plain identifier or your own `[MRV-17 …](url)` link, never a placeholder. - Plain terminology (MRV-159, MRV-75): in Chinese text and figures, keep standard English hardware terms like `fence` / `SFENCE` untranslated — NEVER translate `fence` as 「栅栏」. Avoid vague placeholder jargon like 「慢状态 / 慢态」 (describe the concrete physical cause instead, e.g. 入向桥串行拥塞).

  - Experiment data is a chart plotted from the raw run data, never numbers typed into a drawing: throughput/latency vs W, cores or rate, CDFs, per-stage breakdowns. ## Testbed

- Write the testbed in Rust: host-side and card-side benchmark programs, experiment drivers, and result collection.
- Do not add new C or shell benchmark programs. The C and shell tools in `bench/` (`udp_pingpong`, `udp_blast`, `dpdk_pingpong`, `dpdk_reflector`, testpmd drivers) are prototypes from the first measurements: port their behavior to Rust instead of extending them, and keep them only until the Rust version reproduces their numbers.
- `testbed/` is a Cargo workspace with `members = ["crates/*", "experiments/*"]` and `default-members = ["crates/*"]`:
  - Core crates (`crates/`): `dpdk-sys` (bindgen bindings; DPDK's static inline fast path is exported through bindgen's `wrap_static_fns`, linked statically from `pkg-config --static libdpdk` of the build target; the archives are tracked, so a rebuilt DPDK relinks), `dpdk` (safe layer: `Eal`, `Mempool`, `Port`, `Mbuf`, `Burst`, `Memzone`, `RxQueue`, `TxQueue`, `QueuePair`, `PortStats`, `HostDma`, CN10K coherent CQE peek/direct helpers, `Port::bar0_ptr`, all borrowing `Eal`), `testbed` (shared library: wire format, `closed_loop::ClosedLoop`, `inline`, `lease`, `mmio` incl. `retarget_range`/`detach`, `bar4_nc` `/dev/bar4_mair` MT_NORMAL_NC wrapper, `dsa` Intel DSA portal helper, `hist::FastHist`, `pmu` non-multiplexed `perf_event_open`, `rt` zero-fault `mlockall`/`MPOL_BIND`; plus baseline binaries: `pingpong`/`reflector`, `inline_pingpong`/`inline_reflector`, `inline_stream`, `card_coherency`). Card cores in `inline_reflector` take roles (`--roles ring|source|fetch,...`): `ring` serves the BAR4 request ring, `source` writes card -> host streams, `fetch` reads a host request ring via DPI (`--fetch-dma VF`, `--fetch-chunk`, `--fetch-depth`; speculative unless `FETCH_TRIGGER` + `--via hybrid` doorbells). New DPDK calls go into `FUNCTIONS` in `dpdk-sys/build.rs` (and `wrapper.h` for macros and bitfield structs), never as hand-written `extern` blocks.
  - Experiment crates (`experiments/mrv<N>/`): per-issue Cargo members depending on `dpdk`/`testbed` (and sibling protocol crates where reused, e.g. `mrv259` -> `mrv195`/`mrv206`, `mrv217` -> `mrv212`/`mrv213`). All paper-core experiments (`mrv177`, `mrv190`, `mrv195`, `mrv196`, `mrv206`, `mrv209`–`mrv215`, `mrv217`, `mrv228`, `mrv230`, `mrv231`, `mrv235`, `mrv236`, `mrv245`, `mrv246`, `mrv252`, `mrv253`, `mrv259`) live here and build into the shared workspace `testbed/target/` directory.
  - Auxiliary non-Cargo sources: `testbed/mc-adapter/` (unmodified upstream Memcached 1.6.45 C adapters and build scripts, linked only by Memcached experiment crates via their per-crate `build.rs`) and `testbed/mercury-client/` (remote `mercury` RoCEv2/UDP client Rust + verbs shim sources).
- Build inside devenv, which sets all per-target toolchain variables (and automatically falls back to `../marvell/{marvell-dpdk,sysroot-card}` in secondary jj workspaces): `devenv shell -- sh -c 'cd testbed && cargo build --release'` builds the core `crates/*` for the host (links `marvell-dpdk/build-host`, octeon_ep VF PMD) and the same with `--target aarch64-unknown-linux-gnu` for the card (links the card's `dpdk-24.11-cn10k` from `sysroot-card/` through Ubuntu's `aarch64-linux-gnu-gcc`). Build a specific experiment crate with `-p mrv<N>` (outputs straight to `testbed/target/release/mrv<N>_host` and `testbed/target/aarch64-unknown-linux-gnu/release/mrv<N>_card`), or verify all crates with `cargo check --workspace --all-targets` and `cargo test --workspace --lib`. Pin background builds to Socket 0 (`taskset -c 0-31`) when Socket 1 is running live measurements. Copy card binaries with `scp`; refresh the sysroot with `devenv shell -- card-sysroot-sync` after card package changes. The card's deployed `inline_reflector` is `/root/bench/inline_reflector`: since 2026-11-17 a `main` build with the MRV-26 lease (which `main`'s host tools need); the pre-lease 2026-11-13 build is kept as `/root/bench/inline_reflector.2026-11-13`. Experiments copy their own build under another name.
- Keep `batch` and `concurrency` separate (terminology from `~/dev/accel-datapath`): batch = packets per doorbell (one `rte_eth_tx_burst` call), concurrency = maximum messages outstanding. Every reported number states both, and message rate (Mmsg/s) is reported together with bandwidth.
- Every run must verify its data, not just count it: each reply is matched to its outstanding request (seq + tsc), frames and cells carry a trailing seq copy, and the bins fail on bad or torn replies. Timestamp arrivals with `dpdk::rdtsc_after_loads` (RDTSCP; LFENCE;RDTSC measured the same): plain RDTSC after an MMIO poll executed early and under-measured the inline RTT by ~0.5 µs. Cross-check W=1 RTT against 1 / message rate.
- Host uncore frequency moves W=1 latency by up to ~0.3 µs: it idles at 0.8 GHz and ramps over seconds, so results came in two "modes" (0.92 vs 1.23 µs for the same path). For comparable numbers, pin it first (`sudo bench/host_power.sh pin`: uncore 2.2 GHz on both packages, performance governor on cpu40/104; `restore` undoes it; both leave `current_freq_khz` readable for monitoring). Device-side memory reads in hot loops: read cells word by word (`Cell::poll`), never `read_volatile` of a struct holding a byte array (compiles to 64 byte loads plus a store-forwarding stall).
- Host core frequency: `host_power.sh pin` sets the performance governor on cpu40/104 only; the other node-1 cores ran schedutil (intel_cpufreq passive) when checked on 2026-11-17, and such a core can stay near its 2.2 GHz base clock for seconds after it starts polling (MRV-24: worker lcores that had been idle ran at 2.1–2.2 GHz for the first ~3 s, which made MOVDIR64B look 113 → 76 M/s under bidirectional load and the `split` sender ~32 M/s). EAL's main lcore is the lowest one in `-l` unless `--main-lcore` says otherwise, and `inline_stream` sends from the worker lcore in `bidir`/`split`, so put the core whose rate you measure on cpu40/104 (e.g. `-l 40,41 --main-lcore 41`) or pin it first (`sudo CPU=<n> bench/host_power.sh pin`), and check it with `perf stat -C <cpu> -e cycles,ref-cycles` (GHz = cycles / ref-cycles × 2.2).

## Hardware access

- Root-only host steps live in scripts the user runs with sudo (`bench/host_dpdk_up.sh`, `bench/host_dpdk_down.sh`, `bench/host_power.sh`, `bench/host_boot_persist.sh`).
- Card control path: `ssh root@10.10.0.2` over host PF `ens1` ⇄ card `sdp1-0`. DPDK data path: host VF0 `0000:99:02.0` ⇄ card `sdp1-1` (`0002:01:00.2`). Never give `sdp1-0` to DPDK; that cuts ssh.
- Boot: the card starts its side by itself (`octep-cp-agent.service` runs `/root/octep_up.sh --foreground`; `sdp1-0` 10.10.0.2/24 from `/etc/netplan/60-sdp1-0.yaml`; backups of the files this replaced in `/root/mrv19-backup/`). `sudo bench/host_boot_persist.sh install` makes the host side survive host reboots (octeon_ep at boot, `ens1` 10.10.0.1/24 through systemd-networkd, `perf_event_paranoid`). A card reboot the host did not start leaves `ens1` down for good (octeon_ep only drops the carrier when the heartbeat stops; seen 2026-11-16 after `systemctl reboot` on the card): `sudo bench/host_boot_persist.sh reload` reloads octeon_ep, which resets the card once more, waits for it and recreates the host VFs (verified 2026-11-16: ssh, DPI VFs and host VF0 back in about 1 min with no other step). So reboot the card with `reload` rather than from the card. `sdp1-0`'s MAC changed across the 2026-11-16 reboots (12:7b:e8:6d:89:55 → b6:9f:04:df:07:2e), so never pin a neighbor entry for 10.10.0.2. Not loaded at boot: `pem_wc`, the card's hugepages and `sdp1-1` for DPDK (`/root/bench/dpdk_up.sh`), the host's `bench/host_dpdk_up.sh` and `host_power.sh`.
- A dead card stalls the host's whole network stack on an unpatched octeon_ep (MRV-31, 2026-11-16): after the card's heartbeat stops, the driver still sends every control-mailbox request and waits 8 s for a reply, holding RTNL when the caller is ethtool or a read of `/sys/class/net/ens1/speed`/`duplex`. `tern` and `mailstream` read every interface's `speed` in a loop, so RTNL stayed busy back to back and every RTM_GETLINK dump (`ip link`, `getifaddrs()`, EasyTier) waited for seconds; EasyTier lost its peers. The patch `host-tools/octeon_ep-patches/0001-*` returns `-ENODEV` instead once the heartbeat is lost. On an unpatched driver, do not run `ethtool ens1` or read its `speed` while `ens1` is down.
- Get the user's approval before EBF saves, firmware flashes, and card reboots.
- Card CSRs through `/dev/mem`: only single 64-bit loads of known registers, as `card-scripts/bar4idx7.py` does (`q = (ctypes.c_uint64 * 8192).from_buffer(m)`, then `q[off >> 3]`). Never slice the mmap (`m[o:o+8]`) or iterate the array: a sliced read of BAR4_INDEX15/REG_NORM_ACC on 2026-11-13 raised 5 SEI-UER at once (count 3 → 8), and `list()` over the array raised 14 on 2026-11-10. EDAC logs them seconds late, so recheck the count after ~20 s.
- Host PF BAR4 = 16 × 4 MiB windows into card memory (`BAR4_INDEX` in PEM0 CSRs); firmware points slot i at card physical `0xbfa000000 + i·4 MiB`, the BAR4 space of SDP PF0 (slots 0-7; slot 7 = `0x2fef1` is the octep control mailbox) and PF1 (slots 8-15; slot 15 = `0x2ff71`). Only `inline_reflector` repoints a slot (15) and restores it on exit.
- Host tools map, read or write BAR4 slot 15 only under a lease from the running `inline_reflector` (MRV-26, `testbed::lease`): TCP over the control path to `10.10.0.2:7526` (host `--card`, card `--control`) with a random nonce per run, which the reflector stores in the slot before it answers. Only after that grant does the host map the slot; its first two reads (READY and the nonce) verify the mapping before any other access, and every later read, write or MOVDIR64B follows a `LeasedSlot::check`. No reflector: connection refused (or a 2 s timeout) and BAR4 is never mapped. One host holds the slot at a time (others get BUSY). An exiting reflector takes the lease back and waits for the host to let go before it restores the slot, however long that takes; if it dies (`kill -9`) the host sees the connection close and stops. Map `resource4` only through `Lease::map_slot`.
- `kill -9` of `inline_reflector` leaves slot 15 on its old buffer and its `--store` regions set. The next reflector start, or `inline_reflector --restore` (no EAL), puts back the firmware values (slot 15 = `0x2ff71`, regions 248-255 = 0; `--store` uses at most those 8) before anything else, and refuses while another `inline_reflector` runs.
- Card DPI DMA: PF `0000:06:00.0` (`octeontx2-dpi`), four VFs `0000:06:00.1`-`.4` on vfio-pci: one per `inline_reflector` core for `--dma`, plus one for `--fetch-dma` (approved 2026-11-10 and 2026-11-13; created at boot by `dpi-vfs.service`, `/root/dpi_vfs_up.sh`). DMA writes and reads go out as host VF0 (DPI func pf 0, vf 1) and must target IOVAs in the host DPDK process's memzones; the host IOMMU is on.
- Card core → host stores: PEM0 outbound region table `PEM0_REG_NORM_ACC(i)` at `0x8e00_0000_4000 + 16·i` (256 regions × 2 GiB of core address space at `0x8800_0000_0000 + i·2 GiB`; geometry in `PEM0_CONST_ACC` at `+0x218`), found by disassembling the EBF in `fw-backup/` and decoded with the CN9 BDK headers in coreboot. All zero in EP mode. `inline_reflector --store` claims region `255 - core` per core (approved 2026-11-12), points it at the host reply ring as host VF0 (`vf_active`, vf 0) and restores it on exit. Store only: a load through a region the host does not complete raises an SError. Never read guessed CSR offsets (CN10K offsets differ from the CN9 BDK); reading `0x87e0_0300_1000` (a register only the secure-world EBF reads) caused SEI-UER #3. `--store-wc` maps the regions write-combining through `pem_wc` (loaded first) and stores each reply as 4 contiguous `STP`s: the core gathers them into one 64 B write, ~3× the Device-mapped rate; the host must check every part of a reply, since gathering occasionally fails and the pieces land in any order.
- Write sizes arriving at the host are measurable: `perf stat -a -e 'uncore_iio/event=0x84,ch_mask=0xff,fc_mask=7,umask=1/,uncore_iio/event=0x83,ch_mask=0xff,fc_mask=7,umask=1/,unc_cha_tor_inserts.io_itom'` (line writes, 4-byte data units, full-line ItoM; `nix shell nixpkgs#perf`; needs `kernel.perf_event_paranoid` ≤ 0, set to 0 on saturn since 2026-11-13, kept across host reboots by `bench/host_boot_persist.sh install`). With `umask=4` the same two events count the card's reads of host memory; `event=0xc1`/`0xc0` with `umask=1` count CPU writes to the device (MOVDIR64B).
- Multi-core card side: `inline_reflector -l 3-6 ...` polls with one core per EAL lcore (core i takes ring seqs with `(seq-1) % n == i`), one SDP TX queue per core; the SDP delivers card TX queue i to host VF RX queue i, so the host opens as many RX queues as the card publishes cores (`CORES_OFFSET`) and polls them all.
